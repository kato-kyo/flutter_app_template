# Flutter DDD開発 `ui`ディレクトリ構成

`ui` ディレクトリは、ユーザーインターフェースに関する全ての要素を管理する場所です。
このディレクトリは、プレゼンテーション層として機能し、ユーザーとアプリケーションのビジネスロジック（ドメイン層）との間の橋渡しを担います。

`lib/src/ui/`に配置し、画面グループごとにディレクトリを分けます。

## 構造

```
ui/
 |- [page_group_name]/     # 例: auth, todo など
 |  |- page/            # 画面を表すウィジェット
 |  |- state/           # UI状態管理（Riverpod）
 |  |- widget/          # 再利用可能なUIコンポーネント
```

## 各サブディレクトリの役割

### page/

- アプリケーションの各画面を表すウィジェットを含みます
- 通常は `StatelessWidget` または `ConsumerWidget` として実装
- 例: `login_page.dart`, `todo_list_page.dart`, `todo_detail_page.dart`
- 基本的に状態を持たず、`state/`ディレクトリから提供される状態を消費する役割を担います

### state/

- Riverpodを使用したUI状態管理のためのコード
- `@internal` アノテーション（metaパッケージ）を利用し、UIレイヤー内でのみ使用することを明示
- 例: `auth_state.dart`, `todo_state.dart`
- `.g.dart` ファイルは自動生成されたコードを含む（コード生成ツールによる）
- ドメイン層のサービスを呼び出し、UIに必要なデータを提供

### widget/

- 画面内で使用される再利用可能なUIコンポーネント
- ページよりも小さく、特定の機能に焦点を当てたウィジェット
- 例: `login_form.dart`, `todo_list_item.dart`, `auth_button.dart`
- 可能な限り純粋な表示コンポーネントとして設計（ビジネスロジックを含まない）

## 状態管理の特徴

- Riverpodを利用した状態管理
- `@internal` アノテーションによりUIレイヤー内部での利用に制限
- 各機能（feature）ごとに独立した状態管理
- グローバルな状態が必要ない設計思想

## ドメイン層との連携

- UIレイヤーは直接ドメインエンティティを操作せず、アプリケーション層のサービスを介して操作
- 例: `auth_service.dart`, `todo_service.dart` などを通じてドメインロジックにアクセス
- 双方向データバインディングではなく、単方向データフローを推奨
- **処理が単純な場合**には、applicationレイヤーを経由せず、直接domainのリポジトリへのアクセスを許可
  - 不要な抽象化を避け、コードの簡潔さを維持
  - 例: シンプルなCRUD操作などでは、`todo_repository.dart`に直接アクセス可能

## テスト容易性

- UIコンポーネントは `test/src/ui` ディレクトリ下で対応するテストを持つ
- ドメインロジックとは分離されているため、モックを使用したテストが容易
- ウィジェットテスト、ページテストが実装可能

## まとめ

`ui` ディレクトリは、DDDアーキテクチャにおけるプレゼンテーション層として機能し、ユーザーインターフェースに関連する全ての要素を管理します。Riverpodと`@internal`アノテーションを組み合わせることで、状態管理をUIレイヤー内に制限し、整理されたコード構造を実現しています。このアプローチにより、ドメインロジックとUIの明確な分離が可能となり、テスト容易性と保守性が向上します。
